# MDRAP audit revalidation

This report records the original repository findings and the subsequent revalidation. The authoritative audit file remains unchanged.

| Audit finding | Repository state at revalidation | Evidence | Status | Action |

## Baseline packaging findings before the package migration

- `src/` is a flat collection of top-level modules; hundreds of internal imports use names such as `models`, `pipeline`, and `security`.
- `src/mdrap/api.py` and `src/mdrap/stresstest.py` insert their source directory into `sys.path`.
- `pyproject.toml` explicitly publishes a broad list of generic top-level modules, including `models`, `config`, `api`, `security`, and `cli`.
- Existing modules and tests import each other through those generic names. Replacing the wheel layout safely requires a coordinated package migration and compatibility decision; changing only metadata would make current imports fail or reintroduce application namespace collisions.

## Evidence limits

- Crash reproduction is a single deterministic Windows reproduction, not the required 1,000 randomized crash cycles. Acknowledged-event loss is confirmed; crash safety is not proven.
- The audit-chain tests demonstrate behavior of the current verifier and a caller-supplied checkpoint. They do not establish protection against an attacker who can rewrite the database and replace every checkpoint.
- Feed-path verification found no live source-to-WebSocket route in the server. Endpoints alone are not evidence of a working ingestion runtime.
- The audit's historical performance figures were not rerun. No current end-to-end throughput or latency claim is established here.

## Engineering changes and current evidence

- The Phase 1 fixes are present for hook outcomes and cleanup, audit checkpoint prefix verification, auth lockout isolation, strict non-demo salt enforcement, and visible storage-plus-spill failure.
- `mdrap-core` owns the public API, plugins, adapters, and 25 core modules. `mdrap-contrib` owns 59 peripheral modules and a split `mdrap.cli` package containing 53 handlers in five command groups. `mdrap-compat` is a separate, opt-in distribution containing 83 documented legacy import shims.
- `scripts/verify_import_graph.py` checks that core and contrib module ownership covers the source package, source/contrib CLI copies match, internal imports are relative, no package module touches `sys.path`, and compatibility shims are separate.
- `scripts/verify_release_artifacts.py` built all three wheels and sdists from source archives. Inspected wheel entry counts: core 41, contrib 72, compat 87. Inspected sdist entry counts: core 54, contrib 84, compat 96. Core sdist source ownership is restricted to core modules and adapters; core and contrib wheels expose only the `mdrap` top-level namespace; the compat wheel alone contains generic top-level names.
- `scripts/verify_package_install.py` tested a core-only install with site packages disabled and imported all 25 core modules. It confirmed CLI/peripheral modules are absent from core-only installs, then tested CLI, plugins, a peripheral module, and an application-owned `models.py` alongside core+contrib. A separate install confirmed the opt-in `models` shim aliases `mdrap.models`.
- The full default test run completed with 1,022 passed and 60 deselected (`slow` or `network`) on Windows / Python 3.13.1. Two upstream websockets deprecation warnings were emitted. The audit's Python 3.10–3.13 matrix is configured in CI; only Python 3.13 is available and verified locally.
- The invalid default-suite performance assertion was removed from `test_next_pieces_guarantees.py`: it measured the same pipeline twice, never connected either sink to the pipeline, polled sinks only after timing ended, and used an absolute 500 microsecond/event threshold. It did not constitute an end-to-end benchmark. Reproducible performance measurement remains unverified and belongs to Phase 5.
