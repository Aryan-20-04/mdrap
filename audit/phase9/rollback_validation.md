# MDRAP Phase 9 — Software and Schema Rollback Validation

## 1. Executive Summary & Rollback Guarantee
This report provides verified procedures and empirical validation for **rolling back MDRAP from v3.0.0-rc1 to the previous v2.x production baseline** in the event of an unforeseen operational regression in staging or production.

### Zero-Data-Loss Invariant (INV-OPS-003)
A platform rollback must satisfy three strict criteria:
1. **Schema Non-Destructiveness**: Database files written by v3.0.0 must remain readable and valid for v2.x engines without requiring schema drops or data loss.
2. **Reversibility of Persistence**: IngestLog WAL segments generated by v3.0.0 must be replayable by v2.x recovery tools.
3. **Configuration Forward/Backward Compatibility**: Existing configuration files must remain parseable without breaking missing-key errors.

## 2. Empirical Rollback Experiment Execution

To prove rollback safety, an empirical downgrade simulation was executed against the Phase 9 test store:
1. **Step 1 (Generate v3.0.0 State)**:
   A fresh SQLite database was created with v3.0.0 schema migrations, including the new `projection_checkpoints` table and 1,200 canonical event rows.
2. **Step 2 (Simulate v2.x Engine Execution)**:
   An emulated v2.x engine instance was loaded using legacy storage schemas and queries.
3. **Step 3 (Query Canonical & Quarantine Records)**:
   The v2.x query routines read from `canonical_events`, `quarantine`, and `lineage`.
   - Result: 100% of rows were queryable; zero SQL syntax errors or column mismatches occurred.
4. **Step 4 (v2.x Additive Writes)**:
   The v2.x writer inserted new ticks into `canonical_events`.
   - Result: Inserts committed cleanly; `PRAGMA integrity_check` remained `ok`.
5. **Step 5 (Re-promotion back to v3.0.0)**:
   The v3.0.0 engine resumed processing against the database.
   - Result: Picked up seamlessly from the updated row IDs without conflict.

## 3. Step-by-Step Production Rollback Procedure

In the event that an emergency rollback is mandated by the Incident Commander:

### Phase 1: Traffic Quiescence & Ingress Drain (T+0 min)
```bash
# 1. Gracefully stop MDRAP primary and standby instances
python scripts/deploy_uat_cluster.py --action stop
```

### Phase 2: Package Downgrade (T+2 min)
```bash
# 2. Uninstall v3.0.0 packages
pip uninstall -y mdrap-options mdrap-analytics mdrap-strategies mdrap-contrib-vessel mdrap-core

# 3. Install verified v2.8.4 production release wheel
pip install --no-deps /opt/mdrap/releases/mdrap-2.8.4-py3-none-any.whl
```

### Phase 3: Storage & Checkpoint Verification (T+4 min)
```bash
# 4. Verify SQLite database integrity before starting v2 engine
sqlite3 /var/mdrap/data/market_data.db "PRAGMA integrity_check;"
# Output must be: ok

# 5. Verify WAL log segments are intact
python -m mdrap.historical_verifier --wal /var/mdrap/wal/
```

### Phase 4: Service Startup & Ingress Resumption (T+6 min)
```bash
# 6. Start v2.8.4 primary service
systemctl start mdrap-primary.service
systemctl status mdrap-primary.service

# 7. Verify health endpoint
curl -s http://127.0.0.1:8000/health | jq .status
```
