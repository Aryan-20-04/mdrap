## 1. Executive Summary: Resilience Under Extreme & Degraded Conditions

Institutional market data sidecars must maintain strict isolation boundaries: failure of a client, connection drops, socket saturation, daemon restarts, or storage failures must never cause memory leaks, thread deadlock, or silent data corruption.

Six stress and failure drills were executed against the live MDRAP daemon and Observer components:

| Drill ID | Failure Drill Scenario | Fault Injected | Expected System Behavior | Measured Result | Audit Verdict |
|:---:|:---|:---|:---|:---|:---:|
| **F1** | Sudden Traffic Burst | 25,000 events injected at maximum possible rate | Engine absorbs burst; client recovers all frames | Injected in 10.28s; 25,000 received in 10.33s | **PASS** |
| **F2** | Slow Consumer Eviction | Stalled client stops reading socket | Client queue saturates; daemon evicts stalled client; healthy client unaffected | Slow client evicted after 1,000 dropped ticks; healthy client received 3,000/3,000 | **PASS** |
| **F3** | TCP Disconnect & Reconnect | Client socket forcibly terminated | ObserverClient detects drop, backs off, and reconnects | Reconnected in 0.8s; received 50/50 events post-reconnect | **PASS** |
| **F4** | Daemon Crash & Restart | Daemon process terminated and respawned on same port | Client detects connection loss and reconnects to new daemon instance | Reconnected seamlessly; received 25/25 events from new daemon | **PASS** |
| **F5** | SHM Wraparound & Epoch Reset | Writer laps reader 3x (200 ticks in 64 slots) + epoch ID bumped | Reader detects overrun (None for lapped slots), reads latest slot, catches epoch change | Overrun detected; latest slot valid; epoch change detected | **PASS** |
| **F6** | Exporter File I/O Failure | Export file handle locked / permission restricted | Worker catches OSError, increments error counter, avoids uncaught crash | Survived without process termination; zero unhandled exceptions | **PASS** |

## 2. Detailed Drill Evidentiary Breakdown

### Drill F1 — Sudden Traffic Burst & Queue Recovery
- **Description**: 25,000 ticks were burst-injected across 50 simulated prices at unthrottled maximum speed.
- **Observations**: Injection completed in **10.284 seconds** (2,430.9 EPS). The client drained the queue in **10.335 seconds** (only 51 ms after injection concluded).
- **Result**: Exactly **25,000 / 25,000 events received** (100.0% recovery). Zero deadlocks or dropped records.

### Drill F2 — Slow Consumer Eviction & Client Isolation
- **Description**: A stalled client connected and subscribed to `SUB ALL`, but never invoked `recv()`, causing its OS receive buffer to saturate immediately. A concurrent healthy client ran simultaneously.
- **Observations**: The daemon detected queue saturation (>1,000 dropped frames), logged:  
  `[service] Evicting stalled client (unauthenticated) after exceeding 1000 dropped ticks`,  
  closed the stalled socket, and reclaimed queue resources.
- **Result**: The healthy client was completely isolated and received **3,000 / 3,000 events** with zero dropped ticks.

### Drill F3 — TCP Socket Disconnect & Reconnect Loop
- **Description**: After receiving 50 events, the client's underlying socket handle was abruptly closed (`sock.close()`), simulating an abrupt network failure or link reset.
- **Observations**: `ObserverClient` trapped the socket disconnection in `_run_tcp()`, entered the exponential backoff reconnection loop, re-established the TCP connection, sent `SUB ALL`, and resumed listening.
- **Result**: Exactly **50 / 50 events** were received after reconnection with 1 reconnect logged.

### Drill F4 — Daemon Crash & In-Place Restart
- **Description**: The primary daemon was terminated (`daemon1.stop()`). The client socket was severed. A new daemon instance (`daemon2`) was started on the exact same port.
- **Observations**: `ObserverClient` transparently connected to the replacement daemon instance without requiring process restart or manual intervention.
- **Result**: Exactly **25 / 25 events** generated by the new daemon were received.

### Drill F5 — Lock-Free SHM Ring Buffer Wraparound & Epoch Invalidation
- **Description**: A small 64-slot ring buffer was populated with 200 ticks, wrapping around the ring more than 3 times before consumer attachment. Subsequently, the epoch header was modified to simulate publisher restart.
- **Observations**:
  - Reading slot 1 returned `None` due to publisher overrun detection (`head - seq > slot_count`).
  - Reading the latest published sequence returned the valid, committed tick.
  - Modifying the epoch header triggered `check_epoch_valid() == False`, prompting consumer reattachment.
- **Result**: Overrun and epoch reset detection verified with 100% precision.

### Drill F6 — Exporter File I/O Resilience
- **Description**: File system permissions on active JSONL output files were restricted to simulate permission revocation or disk full conditions during write operations.
- **Observations**: The background exporter worker thread caught the resulting `OSError`, logged a warning, and continued processing queue drain operations without propagating uncaught exceptions to caller threads.
- **Result**: Zero unhandled exceptions. Main application thread remained fully responsive.
